OpenBaton Architecture

动态多模型 Director

从一个用户目标开始，主 agent 或 OpenSpec 持有业务 workflow；OpenBaton 把 OpenCodex 中可用的不同模型变成可授权、可排队、可验收的 host-native subagent 执行链。

00 · Background

为什么需要 OpenBaton

OpenCodex 解决“有哪些模型可以调用”，OpenSpec 解决“复杂工作是什么和进行到哪里”；中间仍缺少安全、动态的多模型执行 director。

1

只有原始 spawn 不够

主 agent 能看到模型和 spawn 工具，却不知道每个模型的权威能力、route 差异、健康度、额度和适用任务。

2

OpenSpec 不负责模型调度

OpenSpec 持有 Goal、Plan、Tasks、Replan 和 Status，但不决定哪个模型执行、允许操作哪些文件、并发和 fallback。

3

Codex 原生 spawn 仍需调度

Codex 提供 host-native subagent 原语；授权、route 分配、并发、验收和上下文卫生仍然需要统一 director。

4

对话需要进入受控 Goal

用户先自由讨论，确认方向后才开始执行。OpenBaton需要把当前对话编译成 Goal Draft 和一次授权单，不要求手动调用 goal-preflight skill。

业务 workflow owner

无 OpenSpec 时是主 agent；有 OpenSpec 时是 OpenSpec。它们决定做什么、计划和业务状态。

→

OpenBaton 的位置

汇聚模型能力证据，编译 Delegation Receipt，选择 route，调度并回收 subagent；不重做业务 Plan。

    03 · Capability Evidence

    模型能力如何进入主 agent 决策

    可用不等于适合。Baton 只提供版本化、可追溯的候选能力证据，不用单一总分替代主 agent 判断。

    OC

    OpenCodex Route Snapshot

    只在配置/catalog 指纹变化或显式 refresh 时更新。

    AA

    Capability Cache

    只在 cache miss、模型/映射/benchmark 版本变化或 TTL 到期时查询 AA。

    BC

    Baton cards

    用户偏好、人工能力说明、显式 canonical mapping 与覆盖。

    RT

    Route runtime

    健康度、额度、延迟、近期成功与失败证据。

    控制面刷新后原子发布本地 Candidate Capability Snapshot；普通任务直接复用 ↓

    本地候选快照

    route identity、mapping confidence、benchmark version、stale 状态与最新 runtime signals。

    →

    主 agent 内的 Baton director

    根据当前 execution unit 选择最合适的模型，不选择“全局最强”。

    →

    Delegation Receipt

    固定模型集合、文件范围、操作类别、重试、fallback 和有效期。

    04 · Authorization

    Baton 持有委派授权，不创造权限

    同一授权层同时适用于有 OpenSpec 和无 OpenSpec。OpenSpec task 表示计划做什么，不自动授权某个模型写文件或执行副作用。

    用户授权
    Execution unit
    最小文件与操作范围
    模型与 host 能力
    有效 worker grant

    Receipt 固定

    • 允许的模型与 provider route
    • read/write allowlist
    • build、network、device、Git 操作
    • attempt、parallel、fork context
    • fallback 与失效条件

    触发 Delta Authorization

    • 模型集合或 provider 改变
    • 文件范围或业务目标扩大
    • 增加 build/test/network/commit
    • 超过重试预算
    • 主 agent Plan 或 OpenSpec task 实质变化

    05 · Dynamic Scheduling

    一次对话中的持续调度循环

    用户无需手动触发 workflow skill。每次 worker 事件、route 状态或业务计划变化后，Baton 都可以重新计算执行优先级。

    01接收 execution unit
    02读取本地 route / capability snapshots
    03主 agent 选择模型
    04编译最小授权
    05排队并 host-native spawn
    06回收短结论与 artifacts
    07主 agent 验收
    08重调度或完成
    ↺ 失败、超时、槽位释放、health/quota 变化、前置完成或业务 Plan 更新，都会回到能力与队列计算。

    06 · Feasibility

    整体实施可行性：PASS / Codex 首版闭环通过

    144/144 回归、全局 ~/.baton 状态、66-route Dynamic Cards、真实 8-ticket FIFO、write completion/error safety gate、OpenSpec stable-number writeback 和 provider no-fallback 日志均已通过。

    已证明的底座

    OpenSpec workflow 命令、OpenCodex provider/catalog、namespaced native spawn、7 个 route、跨轮 session 和并发 6。

    原型闭环已通过

    Conversation-to-Goal、snapshots/cache、Receipt、queue、OpenSpec round-trip、worker 写入与 parent diff gate。

    最终实施结论 · PASS

    Codex adapter 的 route、lifecycle、queue、Receipt、安全、OpenSpec 和打包闭环已完成实测。

    能力判断关键依据
    Conversation-to-Goal原型通过显式提升、讨论态拒绝、excluded 和 Receipt fail-closed 已通过验证。
    OpenSpec workflow已有基础OpenSpec 1.9 已提供 change/spec/status/instructions/validate/archive。
    OpenCodex + native spawn已验证Namespaced route、7 个模型、跨轮 session 和并发 6 已实测。
    能力快照与授权已实现AA Free API 实测写入 608 个唯一模型、32 条显式 mapping；普通调度只读本地 SQLite。
    写代码 worker机制通过shared worktree 已确认；parent diff gate 接受 allowlist 内改动并拒绝越界文件。
    最终方案PASSCodex 首版通过；其它 host adapter 后续分别验证。
    Gate A · 机制与安全

    Shared worktree、diff/import gate、父 Git ownership 和 host capability probe。

    Gate B · 控制面原型

    Goal 提升、snapshots/cache、Receipt、native dispatch、queue 与 no-fallback。

    Gate C · 端到端

    简单任务、复杂无 OpenSpec、复杂 OpenSpec Goal 和写入闭环。

    当前：PASS。Baton 状态全局位于 ~/.baton；Gate A/B/C 已集成并复跑。OpenCodex 按 capability probe 兼容，不锁版本。

    07 · Hard Boundary

    Baton 不跨越的边界

    业务 workflow owner

    无 OpenSpec：主 agent 持有 Goal、Plan、Tasks、Replan 和 Status。

    Baton execution owner

    模型证据、委派授权、route、并发、排队、重试、worker lifecycle 与上下文卫生。
